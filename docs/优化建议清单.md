## 一、性能体验类

### 1. 前台与后台站点列表接口的 D1 串行查询改为并行/批处理
* **现状问题**：
  * 在 [`sites.js`](file:///D:/MY-NAV-GITHUB/functions/api/sites.js#L12-L20) 中，分类列表查询 `catRows` 与站点列表查询 `siteRows` 采用两个连续的 `await ...all()` 串行执行。
  * 在 [`sites.js`](file:///D:/MY-NAV-GITHUB/functions/api/admin/sites.js#L8-L13)（后台）中，存在完全相同的串行 `await` 结构。
  每次请求都需要与 D1 SQLite 实例进行两次连续的网络/进程间往返（Round-Trip）。
* **优化办法**：
  使用 D1 原生支持的批处理 `await env.NAV_DB.batch([catStmt, siteStmt])`，或者使用 `Promise.all([catStmt.all(), siteStmt.all()])` 将两次查询合并为单次往返并发获取。
* **预期收益**：
  前台接口 `/api/sites` 与后台列表 `/api/admin/sites` 的 D1 数据库查询耗时直接降低约 40%～50%，首屏数据呈现速度明显加快。
* **改动量**：小（两处文件各改动 4～6 行）。
* **风险**：无风险。返回的字段、数据解构与下游消费逻辑完全不变。

### 2. 批量书签导入与坚果云恢复的 N+1 串行 SQL 消除
* **现状问题**：
  * 在 [`import.js`](file:///D:/MY-NAV-GITHUB/functions/api/admin/import.js#L24-L38) 中，对导入列表进行 `for` 循环遍历，每条书签都串行执行一次 `SELECT id FROM sites WHERE url = ?`，若分类不存在再执行 `SELECT/INSERT category`，最后再执行一次 `INSERT INTO sites`。
  * 在 [`restore.js`](file:///D:/MY-NAV-GITHUB/functions/api/admin/restore.js#L48-L60) 中，同样存在逐条串行查重并逐条插入的逻辑。
  若用户导入或恢复 100 条书签，将产生 200～300 次顺序 await 的数据库调用，极易触发 Cloudflare Workers 的 CPU 时间上限或网关超时（504）。
* **优化办法**：
  1. 循环前先单次查询全部已有网址放入内存集合：`const existingUrls = new Set((await env.NAV_DB.prepare("SELECT url FROM sites").all()).results.map(r => r.url));`；
  2. 预先拉取并缓存已有分类 Map；
  3. 过滤出待插入数据后，按 50～100 条为一组使用 `env.NAV_DB.batch(insertStmts)` 一次性批量写入。
* **预期收益**：
  将数百次顺序网络往返骤降至 2～3 次批量往返；百级书签导入/恢复耗时从 8～15 秒缩减至 300 毫秒以内，彻底根治超时风险。
* **改动量**：中（重构循环体内的存取方式，补充分批切片）。
* **风险**：低。需遵循 D1 单次 batch 语句数量上限（50～100 条切片即可确保安全）。

### 3. 前台搜索检索与排序评分的单次击键重复计算削减
* **现状问题**：
  在 [`index.html`](file:///D:/MY-NAV-GITHUB/public/index.html#L451-L500) 与 [`index.html`](file:///D:/MY-NAV-GITHUB/public/index.html#L733-L741) 中，搜索框每次触发 `input` 事件都会无防抖地直接调用 `render()`。而在 `render()` 内部：
  1. `visibleSitesList = sites.filter(...)` 调用了全量 `matchSiteScore`；
  2. `visibleSitesList.sort((a,b) => ...)` 在排序比较器中又成倍两两调用 `matchSiteScore`；
  3. `pinnedList` 筛选再次调用；
  4. 遍历所有分类渲染 `catSites` 时（约 10 个分类），每个分类循环内部都再次全量调用 `matchSiteScore`（10 × N 次）；
  5. 左侧边栏 `sidebarNav` 统计每个分类计数时，又再次遍历全量计算。
  以 100 个书签计算，单次击键会导致 `matchSiteScore` 被重复计算高达 2500～3000 次。
* **优化办法**：
  1. 每次搜索关键词变更时，对站点列表做单遍遍历，将分值缓存到对象或 Map 中（如 `scoreMap.get(s)`），后续排序、分类拆分与侧边栏徽标均复用该分值，无需重复算分；
  2. 对 `input` 事件增加轻量微任务防抖（如 `requestAnimationFrame`），避免在中文输入法拼写或连续快速敲击时频繁触发布局重算。
* **预期收益**：
  单次击键的 JS 计算循环减少 85% 以上，低端手机与平板在快速键入时完全摆脱卡顿与微掉帧。
* **改动量**：小（单遍计分并复用结果，约 15 行）。
* **风险**：无。搜索评分与筛选显示规则完全不变。

### 4. 前台首屏静态数据与接口数据一致时的无条件整页重绘消除
* **现状问题**：
  在 [`index.html`](file:///D:/MY-NAV-GITHUB/public/index.html#L1069-L1082) 中，页面在利用 `data.js` 完成第一阶段静态渲染后，异步请求 `/api/sites`。当接口返回后，代码无条件执行：
  ```javascript
  NAV_DATA = data.sites;
  if (Array.isArray(data.categories) && data.categories.length) NAV_CATEGORIES = data.categories;
  selectedSiteIndex = 0;
  render();
  initScrollSpy();
  renderAZStrip();
  ```
  即使线上数据库内容与本地 `data.js` 完全相同，也会完整销毁并重建右侧全部 DOM 节点、重建侧栏索引与字母滑轨，并重新注册监听器。
* **优化办法**：
  在赋值与重新渲染前，加入一层极轻量的数据比对（如比对站点数组长度、首尾 ID、或以 `JSON.stringify` 摘要比对）。如果数据完全一致，直接跳过全量 DOM 销毁与重建。
* **预期收益**：
  常规访问时避免首屏加载后的二次无谓重绘与滚动条微跳，降低浏览器内存抖动与首屏重排开销。
* **改动量**：小（约 6 行防御代码）。
* **风险**：无风险。

## 三、健壮性类（异常处理、边界情况）

### 1. 修改书签接口缺少 URL 重复排重导致 SQLite 唯一约束抛出未捕获 500
* **现状问题**：
  在 [`schema.sql`](file:///D:/MY-NAV-GITHUB/schema.sql#L28) 中定义了 `CREATE UNIQUE INDEX IF NOT EXISTS idx_sites_url ON sites(url)`。
  在新增接口 [`sites.js`](file:///D:/MY-NAV-GITHUB/functions/api/admin/sites.js#L23-L24) 中有严谨的防重检查：
  ```javascript
  const dup = await env.NAV_DB.prepare("SELECT id FROM sites WHERE url = ?").bind(site.url).first();
  if (dup) return json({ error: "这个网址已经在库里了" }, 409);
  ```
  但在修改接口 [`[id].js`](file:///D:/MY-NAV-GITHUB/functions/api/admin/sites/%5Bid%5D.js#L17-L21) 中，**未对修改后的 url 做查重**，直接执行 `UPDATE sites SET ...`。若管理员将某站点的网址改成了库中已有的另一站点网址，D1 会直接抛出未捕获的 SQLite 唯一约束异常，前台收到 500 报错。
* **优化办法**：
  在 `sites/[id].js` 执行 UPDATE 前加入冲突检测：
  `const dup = await env.NAV_DB.prepare("SELECT id FROM sites WHERE url = ? AND id <> ?").bind(site.url, +params.id).first();`，若冲突则返回友好 409 提示。
* **预期收益**：
  消除未捕获的 500 异常，编辑书签时输入重复网址能获得清晰明确的业务提示。
* **改动量**：小（4 行代码）。
* **风险**：无风险。

### 2. 键盘导航定位选择器未转义特殊字符导致潜在 `DOMException` 崩溃
* **现状问题**：
  在 [`index.html`](file:///D:/MY-NAV-GITHUB/public/index.html#L431) 中：
  ```javascript
  const matchEl = document.querySelector(`.card[data-name="${target.name}"]`);
  ```
  如果用户通过导入或添加引入了带特殊字符（例如包含英文双引号 `"`、反斜杠 `\`、方括号 `[]` 等，如 `Vue.js (官方)`、`[精选] 极客工具`）的站点名，当键盘上下键切到或搜索命中该站点时，原生 `document.querySelector` 会直接抛出语法错误：`DOMException: Failed to execute 'querySelector' on 'Document': ... is not a valid selector.`，导致后续键盘事件侦听全部断裂失灵。
* **优化办法**：
  使用标准的 `CSS.escape(target.name)` 进行选择器转义，或改用根据索引/通过 `card.dataset.name === target.name` 进行比对。
* **预期收益**：
  彻底防御书签名称包含任意怪异字符、标点符号时的 JS 运行环境崩溃。
* **改动量**：小（1 行改动）。
* **风险**：无风险。

### 3. AI 简介抓取目标网页缺少响应体大小与 Content-Type 防御
* **现状问题**：
  在 [`ai-desc.js`](file:///D:/MY-NAV-GITHUB/functions/api/admin/ai-desc.js#L43-L45) 中：
  ```javascript
  const r = await fetch(url, ...);
  const html = (await r.text()).slice(0, 200000);
  ```
  虽然有超时控制器，但 `await r.text()` 会先将目标网址返回的全部字节拉入 Worker 内存，然后再取前 20 万字。若用户填入的 URL 指向大文件（如直接指向几百兆的 PDF、音视频或离线安装包），会瞬间吃满 Cloudflare Workers 128MB 的内存上限，导致 Worker 实例直接被边缘宿主干掉。
* **优化办法**：
  1. 检查响应头 `r.headers.get("content-type")`，若不含 `text/html` 则直接快速返回提示；
  2. 利用流式读取器 `r.body.getReader()` 读取前 200KB 内容后主动调用 `cancel()` 关闭连接，不再接收多余数据。
* **预期收益**：
  杜绝非网页 URL 或恶意巨型响应拖垮 Worker 内存，降低外呼流量与 CPU 消耗。
* **改动量**：小（约 10 行）。
* **风险**：无风险。

### 4. 前端书签 HTML 导入缺少文件体积安全上限防御
* **现状问题**：
  在 [`index.html`](file:///D:/MY-NAV-GITHUB/public/index.html#L1031-L1059) 与 [`index.js`](file:///D:/MY-NAV-GITHUB/functions/admin/index.js#L450-L481) 中，用户触发导入时，直接通过 `reader.readAsText(file)` 与 `new DOMParser().parseFromString` 读取并解析整个文件，完全没有检查 `file.size`。若用户不慎误选了几十兆甚至上百兆的非书签文件（如大网页离线包），`DOMParser` 会在主线程长时间阻塞死循环，导致浏览器标签页直接崩溃死锁；在后台更会一次性将数千条条目通过单次 POST 发送给 Worker。

* **预期收益**：
  消除误传大文件导致浏览器主线程无响应、白屏或卡死的极端边界情况。
* **改动量**：小（3 行代码）。
* **风险**：无。真实导出的 HTML 书签文件通常都在数百 KB 以内。

## 四、样式打磨类（纸墨赭石编辑风微雕）

> **本类遵守纪律声明**：以下所有条目均在现有纸墨宣纸、深墨字迹、赭石印鉴风格框架内打磨细节，**完全不改动色彩变量、不自创配色、不推翻任何已定版规则**。

### 1. 书签卡片内超长站名排版截断与外链箭头防挤压对齐
* **现状问题**：
  在 [`style.css`](file:///D:/MY-NAV-GITHUB/public/style.css#L967-L977) 中，`.card-name` 设置了 `display: flex; justify-content: space-between; overflow: hidden; text-overflow: ellipsis; white-space: nowrap;`。
  但查看 [`index.html`](file:///D:/MY-NAV-GITHUB/public/index.html#L415-L418)，卡片站名实际包裹在子元素 `<span>${s.name}</span>` 中。在 CSS 标准里，flex 容器本身的 `text-overflow: ellipsis` 无法作用于其子文本；一旦遇到站名较长的书签，文字不但无法产生「…」截断，还会强行把右侧的外部链接小箭头（`↗`）挤出卡片框或换行错乱。
* **优化办法**：
  在 `.card-name > span:first-child` 上增加 `overflow: hidden; text-overflow: ellipsis; white-space: nowrap; min-width: 0; flex: 1;`，并在 `.card-arrow` 上添加 `flex-shrink: 0; margin-left: 6px;`。
* **改完看起来有什么不同**：
  遇到很长的网站名字（比如学术网站、政府办事平台或长名称项目）时，长文字会在卡片内整整齐齐地被截断并以「…」省略号收尾；而右上角那个赭石小箭头始终稳稳当当待在卡片右上角内侧，绝不会再发生被长文字挤出框外、或者掉到下一行导致卡片忽高忽低的难看现象。
* **改动量**：小（CSS 调整 4 行）。
* **风险**：无。

### 2. 移动端（<960px）双吸顶工具栏重叠打架与遮挡消除
* **现状问题**：
  在 [`style.css`](file:///D:/MY-NAV-GITHUB/public/style.css#L1279-L1285) 与 [`style.css`](file:///D:/MY-NAV-GITHUB/public/style.css#L1332-L1350) 的移动端媒体查询中：
  - A-Z 快速定位滑轨 `.quick-loc-bar` 被设置为 `position: sticky; top: 0; z-index: 100;`；
  - 同时，由左侧边栏演变而来的分类药丸滑动条 `.sidebar-index` 也被设置为 `position: sticky; top: 0; z-index: 50;`。
  两者的吸顶坐标全部是 `top: 0`。当用户在手机上往下滑动页面经过两者时，分类药丸条会直接钻到 A-Z 字母滑轨的正后方，被死死遮住一大半，点不到也看不全。
* **优化办法**：
  在小屏媒体查询下，将 `.sidebar-index` 的吸顶位置精确顺延为 `.quick-loc-bar` 的实际高度下方（设置 `top: 56px`），或利用弹性吸顶层叠规划，让两者互不遮挡、依次排开。
* **改完看起来有什么不同**：
  在手机上往下滑动浏览长页面时，顶部的英文字母滑轨和下方的分类小药丸能整整齐齐地一上一下停在屏幕顶端，再也不会发生下面的药丸滑到上面字母底下被挡住半截、露头露尾点不到的穿模现象。
* **改动量**：小（CSS 微调 1 个数值）。
* **风险**：极低（仅作用于移动端断点）。

### 3. 全站键盘 Tab 键焦点的纸墨风微雕（Focus-visible 规范化）
* **现状问题**：
  在 [`style.css`](file:///D:/MY-NAV-GITHUB/public/style.css) 中，卡片 `.card`、工具栏按钮 `.toggle-view-btn`、`.add-btn`、`.tool-btn` 以及字母滑块 `.az-btn` 均未声明 `:focus-visible` 状态。
  当用户使用键盘 Tab 键在站内导览时，选中的控件直接出现浏览器默认的粗厚亮蓝色光圈，在古朴雅致的米纸底衬与墨线设计中显得极度突兀出戏；而在部分内核下甚至完全看不出焦点停在哪里。
* **优化办法**：
  为主要交互元素统一定义专属的聚焦状态：
  `:focus-visible { outline: 2px solid var(--ochre); outline-offset: 2px; }`，与印章、高亮色保持同一个赭石墨规。
* **改完看起来有什么不同**：
  用键盘按 Tab 键选网站或点按钮时，被选中的地方不再出现刺眼的塑料现代蓝光圈，而是浮现出一道精致规整的赭石色墨线外框，如同盖了一枚小印戳，键盘操作既能一眼看清落点，又与纸墨风浑然天成。
* **改动量**：小（CSS 增加 1 组共用选择器规则）。
* **风险**：无。

### 4. 搜索无匹配空状态的宣纸古籍折页化与文案微调
* **现状问题**：
  在 [`style.css`](file:///D:/MY-NAV-GITHUB/public/style.css#L1076-L1091) 与 [`index.html`](file:///D:/MY-NAV-GITHUB/public/index.html#L118-L121) 中：
  当搜索没有匹配结果时，`.no-results` 仅仅是主画面正中一排干瘪空荡的文字，周围一片空白没有任何边界感；且文案固定写死为「没有找到以『X』开头的站点」（当输入中文词或拼音首字母缩写时依然显示「以……开头」，语义不严密）。
* **优化办法**：
  1. 为 `.no-results` 容器套上纸墨风细虚线墨框，并赋予米宣纸微浅底衬（与常用置顶区的虚线边框统一呼应）；
  2. 顶部衬以小号「暂无收录」古风朱砂印章样式；
  3. 文案优化为通用的「未找到与『...』相符的书签」。
* **改完看起来有什么不同**：
  搜不到东西时，原本像网页出了故障一样的孤零零白板，变成了一个带有细墨虚线框、印着一枚小小红印章的古籍小折页卡片；卡片里的「点击查看全部书签」按钮也更像一颗可以按的纸质小方印，清晰舒适。
* **改动量**：小（约 12 行 CSS + 2 行文案调整）。
* **风险**：无。

### 5. 书签卡片悬停触感顺滑化与夜间模式域名微对比度修正
* **现状问题**：
  1. 在 [`style.css`](file:///D:/MY-NAV-GITHUB/public/style.css#L836-L855) 中，舒适模式与紧凑模式的 `.card` 自身没有声明 `transition` 属性，鼠标滑过时卡片瞬间硬生生地发生位移（`-2px, -2px`），但卡片内部的小箭头却有 0.22s 的缓动动画，导致整体动态脱节发冲；
  2. 在 [`style.css`](file:///D:/MY-NAV-GITHUB/public/style.css#L1005) 中，卡片下方的网站域名 `.card-host` 颜色硬编码写死了浅灰十六进制 `#a1988b`，未走变量。一旦切换到「沉墨」夜间模式，该色块对比度不足，网址显得发灰发虚。
* **优化办法**：
  1. 在 `.card` 上补齐平滑过渡：`transition: transform .14s ease, box-shadow .14s ease, border-color .14s ease;`；
  2. 将 `.card-host` 的颜色收拢为已定版的 CSS 变量 `var(--muted)`。
* **改完看起来有什么不同**：
  鼠标移到任何书签卡片上时，卡片不再像被敲了一下似的突然跳动，而是带着 0.14 秒很温和的微浮起与赭石阴影舒展，手感明显柔和；切到夜间模式后，卡片底部原本模糊不清的英文域名，字迹变得清爽利落、久看不累眼。
* **改动量**：小（改动 3 行 CSS）。
* **风险**：无。

### 6. 分区大标题贯通细墨线跨平台垂直居中修正
* **现状问题**：
  在 [`style.css`](file:///D:/MY-NAV-GITHUB/public/style.css#L781-L819) 中，`.section-head` 声明了 `align-items: baseline`（基线对齐），而右侧伸展的贯通细横线 `.section-line` 是通过 `transform: translateY(-5px)` 强制往上拽。
  因为在 Windows（微软雅黑/中宋）与 macOS/iOS（苹方/宋体）下，28px 辑号与 26px 汉字标题的文字 baseline 高度并不一致，导致这根贯通横线在很多屏幕上直接横切穿过了标题字的腰腹部，或者出现忽高忽低的歪扭错觉。
* **优化办法**：
  将 `.section-head` 整体调整为稳固的 `align-items: center` 居中对齐，移除脆弱生硬的 `translateY(-5px)` 假对齐。
* **改完看起来有什么不同**：
  每一辑分类大标题右边连着的那道贯通墨色细横线，不论在苹果电脑、Windows 还是安卓手机上看，都能严格精准地居中对准大标题的腰线，浑然一体，不再出现线切字腰或忽高忽低的不适感。
* **改动量**：小（调整 2 行 CSS）。
* **风险**：无。

## 五、顺带发现（Bug 隐患与小优化点速记）

1. **后台导出按钮 HTML 标签不合规隐患**：[`index.js`](file:///D:/MY-NAV-GITHUB/functions/admin/index.js#L144-L145) 中使用 `<a><button>导出 JSON</button></a>` 嵌套，属于标准 HTML5 规范禁止的交互标签双重嵌套，会导致部分无障碍工具与键盘聚焦事件紊乱。
2. **后台登录限速的空 IP 边界误锁隐患**：[`login.js`](file:///D:/MY-NAV-GITHUB/functions/admin/login.js#L13) 取不到 `CF-Connecting-IP` 时回退为 `"unknown"`，若在内网调试或特定反代环境下会导致所有未识别 IP 共享一个错误配额，误锁正常登录。
3. **后台 JSON 导出未包含分类树元数据**：[`export.js`](file:///D:/MY-NAV-GITHUB/functions/api/admin/export.js#L39) 的手工 JSON 导出只导出了 `sites` 数组，遗漏了分类层级与排序字段，而 `backup.js` 坚果云备份是有分类树的，两者导出结构未完全对齐。
4. **移动端新增弹窗软键盘遮挡**：在小屏手机上打开「添加网站」弹窗呼出输入法键盘时，底部的「保存到导航」主按钮容易被手机输入法顶到底部遮挡，表单底部需留足 `env(safe-area-inset-bottom)` 缓冲。
