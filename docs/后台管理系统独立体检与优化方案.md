### 提案 01：Google Gemini 预设模型名称不存在导致测试与生成直接 404
* **问题是什么**：
  在后台「伍·AI 补简介设置」中，选择「Google Gemini」服务商时，自动预设的模型名称为 `gemini-2.5-flash`。Google 官方 API 当前在产的稳定模型仅有 `gemini-1.5-flash`、`gemini-2.0-flash` 等，并不存在 `gemini-2.5-flash`。站长若在此处填入有效的 Google API Key 并点击测试生成，将直接收到 Google 端点返回的 `HTTP 404: models/gemini-2.5-flash is not found`，导致该快捷预设完全无法开箱即用。
* **证据在哪**：
  [`functions/admin/index.js` L656](file:///D:/MY-NAV-GITHUB/functions/admin/index.js#L656)：
  ```javascript
  google: { base_url: 'https://generativelanguage.googleapis.com/v1beta/openai/', model: 'gemini-2.5-flash' },
  ```
* **你建议怎么改**：
  将预设模型校正为 Google 官方在产的免费高速模型 `gemini-2.0-flash`（或兼容性最广的 `gemini-1.5-flash`）。
* **预期收益**：
  修复核心预设缺陷，站长填入免费 Gemini 密钥后当场跑通测试，不再被 404 假故障困扰。
* **风险或代价**：无风险，无成本。
* **自评优先级**：**高**

### 提案 02：环境与 KV 切换时密码留空导致空值覆盖与失效陷阱
* **问题是什么**：
  当站长原先通过环境变量配置了 WebDAV 密码或 AI Token 时，后台页面会显示「环境变量生效中」，密码框占位符显示 `已设置 (••••xxxx)，留空不改`。
  如果站长此时想将配置迁移到后台 KV 保存，或者想在后台补充 URL，自然会将密码框留空提交。
  但在后端 [`functions/api/admin/config.js` L40-L51](file:///D:/MY-NAV-GITHUB/functions/api/admin/config.js#L40-L51) 与 [L65-L78](file:///D:/MY-NAV-GITHUB/functions/api/admin/config.js#L65-L78) 中：
  ```javascript
  const prevWd = kv.webdav || {};
  let newPass = prevWd.pass || "";
  if (typeof body.webdav.pass === "string" && body.webdav.pass.trim() !== "") {
    newPass = body.webdav.pass.trim();
  }
  ```
  `prevWd` 仅从 `kv.webdav` 取值。如果 KV 之前未保存过配置，`newPass` 直接沦为空字符串 `""`。
  系统看似保存成功，但 KV 里实际存入的是空密码。未来站长一旦在 Cloudflare 控制台删除环境变量、以为能无缝由后台配置接管时，WebDAV 备份与 AI 生成会瞬间瘫痪。
* **证据在哪**：
  - 后端合并逻辑：[`functions/api/admin/config.js` L41-L51](file:///D:/MY-NAV-GITHUB/functions/api/admin/config.js#L41-L51) 与 [L66-L78](file:///D:/MY-NAV-GITHUB/functions/api/admin/config.js#L66-L78)。
  - 前端提示给用户造成误解：[`functions/admin/index.js` L704, L716](file:///D:/MY-NAV-GITHUB/functions/admin/index.js#L704)。
* **你建议怎么改**：
  在保存接口中防御判断：若当前 KV 中没有密码记录，且请求中也没有提交新密码：
  1. 若当前环境变量存在密码，允许在站长首次保存时自动将环境变量生效的密码写入 KV，或者
  2. 若 KV 为空且用户未输密码，直接在保存时拦截并提示：`检测到这是您首次在后台保存该配置，请重新输入一次密码以存入 KV`。
* **预期收益**：
  杜绝「界面提示已设置留空不改，后端却静默写入空字符串」的数据踩坑现象，保证凭证交接万无一失。
* **风险或代价**：改动小，需保证环境变量明文不主动回显给前端。
* **自评优先级**：**高**

### 提案 03：WebDAV 连通性测试针对全路径备份文件 URL 误报 404 阻断配置
* **问题是什么**：
  后台在自定义 WebDAV 预设的提示文案中写明：`请输入 WebDAV 目录或 backup.json 文件完整地址`。
  如果站长按提示填写了完整文件路径（如 `https://dav.example.com/backup/rixin-jilan-backup.json`）并点击「测试连接」，`test-webdav` 接口会直接向该 URL 发送 `PROPFIND`（Depth: 0）。
  如果这是站长首次配置、远程还没有该备份文件，WebDAV 服务器标准规范必定返回 `HTTP 404 Not Found`。
  此时 `test-webdav` 判定 `r.ok || r.status === 207` 为假，直接报错 `WebDAV 服务器返回状态码 HTTP 404`，误报测试未通过。站长会误以为账号密码或地址填错，陷入不敢保存的死循环。
* **证据在哪**：
  - 前端提示文案：[`functions/admin/index.js` L694](file:///D:/MY-NAV-GITHUB/functions/admin/index.js#L694)。
  - 后端测试逻辑：[`functions/api/admin/config/test-webdav.js` L42-L64](file:///D:/MY-NAV-GITHUB/functions/api/admin/config/test-webdav.js#L42-L64)。
* **你建议怎么改**：
  在 `test-webdav.js` 发起 `PROPFIND` 前，如果 URL 以 `.json` 结尾，先截取其父级目录作为探测目标（或者在返回 404 时对父目录回退探测一次）；只要父级目录存在且认证通过，即视为连通正常。
* **预期收益**：
  消除新站首次配置时的「404 假阻断」，自定义文件地址也能顺利通过测试。
* **风险或代价**：改动约 8 行代码，逻辑完全向后兼容。
* **自评优先级**：**高**

### 提案 04：搜索过滤状态下拖拽或上下调序导致分类内排序永久错乱
* **问题是什么**：
  当站长在右侧书签列表的搜索框输入关键词过滤时，页面仅渲染命中的书签。
  此时如果点击「↑」「↓」箭头或进行拖拽排序，前端会将仅包含这几条筛选结果的数组 ID 发送给 `/api/admin/reorder`。
  后端会将传过去的 ID 赋予递增序号（10, 20...），而在该分类下因搜索被隐藏的其他书签的 `sort_order` 则保持原值不变。
  这会导致显式调整的书签与隐藏的书签在序号上严重混叠、穿插冲突，清空搜索框后整个分类的书签顺序直接乱套。
* **证据在哪**：
  - 前端搜索后数据切片与提交：[`functions/admin/index.js` L378-L380, L420-L421, L470-L481](file:///D:/MY-NAV-GITHUB/functions/admin/index.js#L378)。
  - 后端直接按传入数组重排：[`functions/api/admin/reorder.js` L46-L48](file:///D:/MY-NAV-GITHUB/functions/api/admin/reorder.js#L46-L48)。
* **你建议怎么改**：
  1. 防呆拦截法（最稳）：在 `siteSearch` 输入框有内容时，禁用拖拽手柄并给「↑」「↓」按钮添加 `disabled` 及 tooltip 提示：`当前处于搜索过滤状态，请清空搜索关键词后再调整书签顺序`。
  2. 完整投影法：前端在重排时，将移动操作完整投影到原分类全量数组中，再将全部分类的 ID 列表提交给后端。
* **预期收益**：
  杜绝搜索状态下调序引发的静默数据紊乱。
* **风险或代价**：推荐方案 1，改动仅需 5 行代码，防呆逻辑清晰直观。
* **自评优先级**：**高**

### 提案 05：分类拖拽在 Drop 后未重新渲染导致子分类所属父级视觉穿插错位

  对比同文件中的 `moveCat` 按钮回调在 [L311](file:///D:/MY-NAV-GITHUB/functions/admin/index.js#L311) 明确执行了 `renderCats()`，而 `ondrop` 只做了 DOM 插入与 toast，漏掉了 `renderCats()`。
* **你建议怎么改**：
  在 `ondrop` 成功回调中补上 `renderCats()`，重新按树形算法规范排布表格 DOM。
* **预期收益**：
  消除拖拽分类后的 DOM 树形错位与视觉穿插。
* **风险或代价**：改动 1 行代码，无风险。
* **自评优先级**：**中**

### 提案 06：WebDAV 连通性测试在 URL 变更时盲目复用旧密码导致凭据跨站嗅探隐患
* **问题是什么**：
  在 [`functions/api/admin/config/test-webdav.js` L19-L25](file:///D:/MY-NAV-GITHUB/functions/api/admin/config/test-webdav.js#L19-L25) 中：
  ```javascript
  const activeCfg = await getWebdavConfig(env);
  if (!targetPass && activeCfg && activeCfg.pass) {
    targetPass = activeCfg.pass;
    if (!targetUrl) targetUrl = activeCfg.url;
    if (!targetUser) targetUser = activeCfg.user;
  }
  ```
  如果站长原本配置了坚果云，现在想测试一个外部新的 WebDAV 地址，在输入框填了新地址 `https://other-dav.com` 且留空了密码并点击测试。
  由于 `targetPass` 为空，后端会直接取出站长在坚果云的应用密码，组装成 Basic Auth 发往 `other-dav.com`。这在安全原则上属于跨域凭据无意泄露（Credential Exposure）。
* **证据在哪**：
  [`functions/api/admin/config/test-webdav.js` L19-L25](file:///D:/MY-NAV-GITHUB/functions/api/admin/config/test-webdav.js#L19-L25)。
* **你建议怎么改**：
  增加同源域名校验：只有当请求中的 `targetUrl` 域名与 `activeCfg.url` 域名完全一致时，才允许复用已存密码；如果域名发生变化且未填新密码，直接返回校验错误：`检测到地址已更改，请填写对应的新密码`。
* **预期收益**：
  防止站长在测试第三方或自建服务时将已有网盘的敏感应用密码错发给未知主机。
* **风险或代价**：改动 3 行代码，安全性提升。
* **自评优先级**：**中**

### 提案 07：本地 JSON 备份缺乏恢复入口（只许导出不许导入，灾备闭环断裂）
* **问题是什么**：
  在「陆·导入 / 导出」卡片中，提供了「导出 JSON」功能，导出的 `rixin-jilan-export.json` 完整包含了分类树（父级关系、私密标记、排序号）和书签的所有元数据。
  但卡片里的导入功能却只支持 `.html,.htm` 格式的浏览器书签。
  这意味着：如果站长未开通或不想使用 WebDAV，即使本地下载了全量 JSON 备份，一旦数据库出故障，在后台**根本找不到任何入口把这个 JSON 导回系统**！系统的本地灾备闭环是断裂的。
* **证据在哪**：
  [`functions/admin/index.js` L204-L209](file:///D:/MY-NAV-GITHUB/functions/admin/index.js#L204-L209)：
  `<input type="file" id="importFile" accept=".html,.htm">`。且后端 `restore.js` 已具备完整的 JSON 反序列化与入库能力，但仅绑定了 WebDAV 请求。
* **你建议怎么改**：
  1. 将文件选择器扩展为 `accept=".html,.htm,.json"`；
  2. 当站长选择 `.json` 文件时，读取并在前端解析出 `categories` 与 `sites`，调用现有的导入或恢复批量逻辑落库。

## 特别附录：刚写完的「设置中心」代码里，最不放心的三处深层坦白

在审阅刚刚写完并上线的设置中心模块（配置读写、WebDAV 连通性测试、AI 适配与连通性测试）代码时，我认为**最值得核验、最不放心的三处隐患**如下：

### 1. Google Gemini 预设模型名称笔误写成了未发布的 `gemini-2.5-flash`（已列为提案 01）
* **坦白位置**：[`functions/admin/index.js` L656](file:///D:/MY-NAV-GITHUB/functions/admin/index.js#L656)
* **不放心原因**：
  在编写 `AI_PRESETS` 快捷字典时，原意是填写 Google 官方最新的高速模型，手误写成了尚未公开发布的 `gemini-2.5-flash`。
  由于在本地测试时使用了 Cloudflare Workers AI 原生协议与 DeepSeek 验证通路，未用真实的 Google API Key 跑 Gemini 预设端点，导致这个模型名称笔误溜进了主干。
  站长使用时只要切到 Google Gemini，测试必挂（404）。核验时请着重看这一行。

### 2. WebDAV 测试在密码框留空时，存在把旧密码送往新域名的跨站嗅探风险（已列为提案 06）
* **坦白位置**：[`functions/api/admin/config/test-webdav.js` L19-L25](file:///D:/MY-NAV-GITHUB/functions/api/admin/config/test-webdav.js#L19-L25)
* **不放心原因**：
  为了实现「密码框留空表示保持原值不修改」的贴心体验，在 `test-webdav.js` 中做了自动回退：若传入的 `pass` 为空，就去读取系统当前已生效的 `activeCfg.pass`。
  但是当时忽略了一个关键边界：**如果站长同时在前端改写了 WebDAV 的 `url` 呢？**
  如果站长改写了 `url` 为另一个全新域名，却把密码框留空点击测试，系统会毫无保留地把站长原本保存在坚果云的应用密码发往新域名的服务器。在网络安全规范中，这种跨域凭证复用是严重的不规范设计。

### 3. 环境变量与 KV 优先级交接时的空密码覆盖死锁（已列为提案 02）
* **坦白位置**：[`functions/api/admin/config.js` L41-L51, L66-L78](file:///D:/MY-NAV-GITHUB/functions/api/admin/config.js#L41-L51)
* **不放心原因**：
  虽然严格遵守了「环境变量优先于后台 KV」的定版规矩，但忽略了「站长打算从环境变量平滑降级到 KV」的操作心理。
  前端界面的占位符写着 `已设置 (••••xxxx)，留空不改`，给站长的心理暗示是「我不填，系统就会帮我兜着这个密码」。
  然而后端逻辑只在 `kv.webdav` 内部做留空继承，根本不会（也确实无法安全地）去继承环境变量里的密码。结果就是站长留空保存后，KV 里被堂而皇之地存进了一个空字符串 `""`。
  只要环境变量一删，整个服务立刻哑火。这种两层配置交接处的断层，是我写完后反复核对觉得最容易让人掉坑的死角。
