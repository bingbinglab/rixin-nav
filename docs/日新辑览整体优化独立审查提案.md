### 提案 01：前台验身原地解锁被 HTTP 缓存劫持致私密书签无法即时展示

1. **问题点**：未登录访问 `/api/sites` 响应头下发了 `Cache-Control: public, max-age=30` 且缺失 `Vary: Cookie`，导致站长原地登录成功后 30 秒内无法解锁展示私密书签。
2. **证据**：
   - [`functions/api/sites.js` L59-L60](file:///D:/MY-NAV-GITHUB/functions/api/sites.js#L59-L60)：
     ```javascript
     const cacheHeaders = authed ? {} : { "Cache-Control": "public, max-age=30, stale-while-revalidate=120" };
     return json({ categories, sites, authed }, 200, cacheHeaders);
     ```
   - [`public/assets/app.js` L846, L882](file:///D:/MY-NAV-GITHUB/public/assets/app.js#L846)：
     ```javascript
     // 验证成功：原地关闭弹窗，刷新数据以解锁私密书签
     if (loginModalOverlay) loginModalOverlay.hidden = true;
     await refreshSitesData();
     ...
     const r = await fetch('/api/sites', { headers: { 'Accept': 'application/json' } });
     ```
   - **复现机理**：访客或未登录站长首次打开前台，浏览器自动发起 `fetch('/api/sites')`，服务端返回包含 `max-age=30` 的强缓存头。若站长在 30 秒内点击「门牌」输入口令完成登录，随后执行 `refreshSitesData()` 时，因 30 秒强缓存仍在有效期内，浏览器网络栈直接命中本地缓存返回未登录的旧数据（服务端根本收不到带 Cookie 的新请求）。`authed` 依旧为 `false`，私密书签无法显示，门牌未切换为掌柜，造成“登录成功却看不见私密书签”的假故障。
3. **建议改法**：
   - 服务端 [`functions/api/sites.js`](file:///D:/MY-NAV-GITHUB/functions/api/sites.js)：未登录时响应头补充 `"Vary": "Cookie"`，并将 `public` 改为 `"private, max-age=30, stale-while-revalidate=120"`；已登录时明确指定 `"Cache-Control": "private, no-store"`，防止任何 CDN 边缘节点混淆。
   - 客户端 [`public/assets/app.js`](file:///D:/MY-NAV-GITHUB/public/assets/app.js)：在 `refreshSitesData` 的 `fetch` 选项中添加 `cache: 'no-cache'`（或在显式重新拉取时拼接时间戳 `?_t=${Date.now()}`），彻底防止本地强缓存拦截。
   - **手机端特别适配**：手机端浏览器（如 iOS WebKit Safari）对强缓存的管理更激进，且在应用切换回前台时常直接读取内存镜像。加入 `cache: 'no-cache'` 与时间戳穿透，能确保手机端站长验身完毕后 100% 当场看到私密书签展卷，绝不受移动端激进缓存干扰。
4. **预估收益**：彻底根治原地验身后 30 秒内的缓存幽灵故障，确保登录后 100% 立即展示私密书签，私密防线与鉴权表现精准无误。
5. **风险或代价**：无。

### 提案 02：后台 AI 设置中 Google Gemini 预设模型不存在报 HTTP 404

1. **问题点**：后台「伍·AI 补简介设置」中选择 Google Gemini 时，自动填入的预设模型为 `gemini-2.5-flash`，该模型在 Google 官方 API 中并不存在，导致测试与补简介直接 404 失败。
2. **证据**：
   - [`public/admin-assets/admin.js` L1671](file:///D:/MY-NAV-GITHUB/public/admin-assets/admin.js#L1671)：
     ```javascript
     google: { base_url: "https://generativelanguage.googleapis.com/v1beta/openai/", model: "gemini-2.5-flash" },
     ```
   - **外部一手出处**：Google 官方 Gemini API 模型指南（[https://ai.google.dev/gemini-api/docs/models/gemini](https://ai.google.dev/gemini-api/docs/models/gemini)，页面核验日期：2026 年最新），官方现役高性价比模型为 `gemini-2.0-flash` 与 `gemini-1.5-flash`，官方模型库中并无 `gemini-2.5-flash`。
   - **现象复现**：站长填入官方免费 API Key 点击「测试生成」，直接收到 Google 端点报错：`HTTP 404: models/gemini-2.5-flash is not found`。
3. **建议改法**：
   - 将 [`admin.js` L1671](file:///D:/MY-NAV-GITHUB/public/admin-assets/admin.js#L1671) 中的 `model: "gemini-2.5-flash"` 改为 `model: "gemini-2.0-flash"`。
   - **手机端特别适配**：测试返回的内容卡片（`#aiTestResult`）在手机窄屏（375px）下设置 `word-break: break-all; white-space: normal;`，防止模型返回长文本或测试错误日志撑破手机视口导致横向异常滚动。
4. **预估收益**：修复预设缺陷，站长选用免费 Google Gemini 密钥后当场跑通测试，不再被 404 假故障阻断。
5. **风险或代价**：无。

### 提案 03：单条新增书签排序号恒为 0 导致被顶到分类最前位

1. **问题点**：后台单条新增书签时请求体未带 `sort_order`，服务端清洗兜底赋 0，导致新录入的书签始终插在分类的最顶端（第一条），打乱原有顺序且造成 0 序号扎堆。
2. **证据**：
   - [`functions/api/admin/sites.js` L23-L30](file:///D:/MY-NAV-GITHUB/functions/api/admin/sites.js#L23-L30)：新增插入时直接使用 `site.sort_order`。
   - [`functions/_lib/util.js` L90](file:///D:/MY-NAV-GITHUB/functions/_lib/util.js#L90)：`sort_order: Number.isFinite(+body.sort_order) ? +body.sort_order : 0`。
   - [`public/admin-assets/admin.js` L1335-L1336](file:///D:/MY-NAV-GITHUB/public/admin-assets/admin.js#L1335-L1336)：新增模式下 `id` 为空，前端从未传递 `sort_order`。
   - 对比现行代码：在批量移动接口 [`functions/api/admin/sites/batch.js` L49-L55](file:///D:/MY-NAV-GITHUB/functions/api/admin/sites/batch.js#L49-L55) 中，采用查出 `COALESCE(MAX(sort_order), 0)` 并递增追加。
3. **建议改法**：
   - 在 [`functions/api/admin/sites.js`](file:///D:/MY-NAV-GITHUB/functions/api/admin/sites.js) 的 `onRequestPost` 中，当未传入显式排序号时，查询 `SELECT COALESCE(MAX(sort_order), 0) AS max_sort FROM sites WHERE category_id = ?`，将新书签的 `sort_order` 赋为 `max_sort + 10`。
   - **手机端特别适配**：在手机端操作「新增·编辑」Tab 成功保存后，调用 `switchTab("tab-sites")` 切换回书签列表时，高亮并平滑定位（`scrollIntoView({ behavior: 'smooth', block: 'center' })`）到末尾新插入的卡片行，站长在手机上即可瞬间核验新增效果，无需在手机长列表中手动滑到最底端寻找。
4. **预估收益**：新录入的书签自然排列在分类末端，符合“后录入的排在后面”的正常心智习惯，彻底消灭新增书签导致的 0 序号同位冲突。
5. **风险或代价**：无。

### 提案 04：WebDAV 凭据 Base64 遇非 Latin-1 字符报 500 崩溃隐患

1. **问题点**：WebDAV 凭据拼装直接使用原生 `btoa`，若密码或账号中包含特殊符号、中文或非 Latin-1 字符，Worker 将抛出原生 `DOMException` 导致整站 500 崩溃。
2. **证据**：
   - [`functions/api/admin/backup.js` L41](file:///D:/MY-NAV-GITHUB/functions/api/admin/backup.js#L41)：`const auth = "Basic " + btoa(`${cfg.user}:${cfg.pass}`);`
   - [`functions/api/admin/restore.js` L19](file:///D:/MY-NAV-GITHUB/functions/api/admin/restore.js#L19)：`const auth = "Basic " + btoa(`${cfg.user}:${cfg.pass}`);`
   - [`functions/api/admin/config/test-webdav.js` L80](file:///D:/MY-NAV-GITHUB/functions/api/admin/config/test-webdav.js#L80)：`const authHeader = "Basic " + btoa(`${targetUser}:${targetPass}`);`
   - [`functions/_lib/util.js` L101](file:///D:/MY-NAV-GITHUB/functions/_lib/util.js#L101)：`auth: "Basic " + btoa(env.WEBDAV_USER + ":" + env.WEBDAV_PASS),`
3. **建议改法**：
   - 在 [`functions/_lib/util.js`](file:///D:/MY-NAV-GITHUB/functions/_lib/util.js) 中封装安全的 UTF-8 转 Base64 函数：
     ```javascript
     export function toBase64(str) {
       return btoa(unescape(encodeURIComponent(str || "")));
     }
     ```
   - 全仓统一调用该函数生成 Basic Auth 头，彻底替换裸调 `btoa`。
   - **手机端特别适配**：在手机触屏上输入复杂密码（如坚果云随机生成的应用密码）时，手机剪贴板粘贴往往容易带入零宽空格、全角冒号或特殊符号。加入编码安全转换可确保手机端填写的密码绝对不会诱发服务端崩溃。
4. **预估收益**：彻底防御特殊密码字符引发的未捕获异常，容灾与备份通道健壮性显著增强。
5. **风险或代价**：无。

### 提案 05：前台键盘 Enter 键无条件拦截破坏按钮原生可访问性

1. **问题点**：前台全局键盘监听在按下 Enter 键时，无视当前激活元素是否为按钮，直接调用 `e.preventDefault()` 并强制开网页，导致键盘 Tab 聚焦到页面按钮时无法回车触发。
2. **证据**：
   - [`public/assets/app.js` L601-L610](file:///D:/MY-NAV-GITHUB/public/assets/app.js#L601-L610)：
     ```javascript
     if (e.key === 'Enter') {
       if (visibleSitesList.length > 0) {
         e.preventDefault();
         const targetSite = visibleSitesList[selectedSiteIndex] || visibleSitesList[0];
         if (targetSite && targetSite.url) {
           window.open(targetSite.url, '_blank', 'noopener');
         }
       }
       return;
     }
     ```
   - **现象复现**：当用户使用键盘 Tab 键选中「切换白天/夜间模式」按钮、紧凑模式切换按钮或侧边栏链接并按下回车，预期的按钮点击事件被强行阻止，反而突兀地在新标签页打开了第一个书签网站。
3. **建议改法**：
   - 增加当前焦点元素判定：
     ```javascript
     const activeTag = (document.activeElement && document.activeElement.tagName) || '';
     if (activeTag === 'BUTTON' || activeTag === 'A') return; // 放行按钮与超链接原生 Enter 点击
     ```
   - **手机端软键盘重点适配**：
     - 在 iOS/Android 手机端，当用户在搜索框输入完毕并点击手机软键盘右下角的「前往 / 搜索 (Go/Search)」时，也是触发 Enter 键事件。
     - 若当前匹配列表中有结果，不仅执行在新标签打开目标网址，而且必须调用 `input.blur()` **强制收起手机软键盘**！若不主动收起软键盘，用户退回导航站时，软键盘仍占据着手机下半屏（达 40%~50% 视口高度），严重破坏手机端浏览体验。
4. **预估收益**：规范 Web 键盘交互与无障碍标准，彻底杜绝回车误跳现象；手机端软键盘自动收起干净利落。
5. **风险或代价**：无。

### 提案 06：前台登录遇环境配置缺失返回纯文本导致错误信息失真

     }

### 提案 20：前台卡片悬浮增设「誊录网址」一键复制轻交互

1. **机会点**：提供无需新开标签页、直接快速拷贝站点网址的优雅途径，契合将书签分享给好友的高频场景。
2. **证据**：
   - [`public/assets/app.js` L230-L244](file:///D:/MY-NAV-GITHUB/public/assets/app.js#L230-L244)：卡片右上角目前只有外链符号 `↗`。

   - **触屏无 `:hover` 痛点破局**：触屏手机没有鼠标悬停，如果靠 hover 显现，手机用户永远按不到。
   - **触屏双轨适配策略**：
     - **视觉触控轨**：在触屏模式下（`@media (hover: none)`），右上角复制小图标 `⎘` 设为半透常驻（35% 不透明度），配备独立的 $\ge 36\times 36\text{px}$ 触控响应区，点击时调用 `e.preventDefault(); e.stopPropagation();` 仅复制网址而不跳转；

4. **预估收益**：高频工具分享极其轻快，不打破站长日常浏览心流；手机触屏操作无论点按还是长按均无比顺手。
5. **风险或代价**：无。

### 提案 21：前台按键速查便签浮层（按下 `?` 呼出「检字诀」）

1. **机会点**：前台蕴藏着极为高效的全局键盘交互，通过按下 `?` 弹出一页精美的便签式速查手册，提升探索感与仪式感。

     - **手机端**：在快速定位条上的 `※` 标设立可点击热区（$\ge 36\times 36\text{px}$），点击弹出的不是按键表，而是专属的**《日新辑览 · 触控捷径》**：
       - `[ 滑动字母 ]` 极速定位拼音首字母；
       - `[ 横滑胶囊 ]` 快速穿梭各大专辑；
       - `[ 长按卡片 ]` 誊录站点网址；
       - `[ 轻按右下 ]` 浮印一键登顶。
4. **预估收益**：桌面端满足极客键盘流，手机端呈现典雅的手势锦囊，产品质感高度统一。
